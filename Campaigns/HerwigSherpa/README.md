# Herwig Colour and Shower Comparison with Sherpa

This campaign compares the Herwig 7.3 QCD-instanton implementation with
Sherpa 3.0.4 in `gg` and all supported strong initial states, for both low-
and high-mass samples. It separates a Herwig colour-flow variation from a
Herwig shower variation and uses the repository's Rivet analysis as the common
particle-level comparator.

The physics configuration is in [`campaign.json`](campaign.json). Canonical
cards are generated by [`run_campaign.py`](run_campaign.py) and committed so
that every setting remains inspectable.

## Samples

| Sample ID | Flavour model | Colour model | Shower |
| --- | --- | --- | --- |
| `herwig` | VariableKKS | Random3 | Angular |
| `herwig-qcdinsplanar` | VariableKKS | QCDINSPlanar | Angular |
| `herwig-random3-dipole` | VariableKKS | Random3 | Dipole |
| `sherpa` | Sherpa thresholds | Sherpa native | CSS |

`herwig` remains the baseline sample ID, so its card paths, output paths, and
stable seeds are unchanged. Comparing it with `herwig-qcdinsplanar` isolates
the colour-flow model. Comparing it with `herwig-random3-dipole` measures a
full shower-model variation.

QCDINSPlanar is inspired by QCDINS 2.0. It pairs fermion colour sources and
sinks and distributes every gluon on a planar string anchored by at least one
fermion endpoint. Random3 instead randomizes all incoming and outgoing colour
and anticolour ends together. Neither is a first-principles prediction of the
exclusive instanton colour flow; their difference is a model systematic.

The dipole sample switches to Herwig's `DipoleShowerHandler` and loads the
native `Dipole_AutoTunes_gss.in` tune. That tune changes shower alpha_s,
infrared cutoffs, constituent masses, and hadronization parameters. The card
then restores the campaign PDFs, MPI-off setting, Random3, and quark-mass
convention. It should therefore be interpreted as a complete shower and tune
variation, not only a different recoil map.

The standard five-flavour dipole shower requires the canonical `u,d,s,c,b`
particle data to be massless for PDF legs and initial-state radiation. The
dipole cards therefore set their nominal masses to zero and retain the
requested zero-mode masses as `HardProcessMass`. `MEInstanton` detects that
difference and creates private physical-mass particle data for outgoing hard
quarks only. Thus incoming quarks remain massless, while MAMBO and the event
record keep the requested outgoing masses.

Herwig's stock massive final-state kernels replace the post-emission quark
with the canonical flavour data, which would erase that physical mass. The
campaign plugin supplies just two emitter-preservation adapters, for
final-final and final-initial quark radiation. They inherit Herwig's native
splitting functions, massive kinematics, CMW scheme, and PDF-ratio machinery;
only the returned emitter particle data differ. The final-final adapter also
covers a massless secondary quark recoiling against a massive zero mode, the
mixed-mass case not accepted by the stock all-massless selector. The adapter
source is tracked in
[`InstantonDipoleKernels.cc`](../../InstantonDipoleKernels.cc).

## Common Physics Definition

| Setting | Value |
| --- | --- |
| Collision energy | `13 TeV` |
| PDF | `NNPDF31_nnlo_as_0118`, member 0 |
| Scale | `mu^2 = shat/<N_g>` |
| Gluon distribution | KKS Poisson mean, modifier 1 |
| Literal final-parton cap | 29 |
| MPI | Off |
| Low mass | `30..2895.5 GeV` |
| High mass | `500..2895.5 GeV` |
| Events per low profile | 50,000 |
| Events per high profile | 20,000 |
| Shards | 10 per sample/profile |

The four process/region profiles are `gg-low`, `gg-high`, `all-low`, and
`all-high`. Each sample contains 140,000 events, giving 560,000 events in 160
production shards.

Both generators use the requested outgoing zero-mode masses:

```text
u = 0.0023, d = 0.005, s = 0.093, c = 1.27, b = 4.18 GeV.
```

Herwig uses MAMBO, `GluonCounting FinalState`, `NAdditional 25`,
`MaxFinalPartons 29`, and `General` angular-shower reconstruction. MPI is
disabled explicitly for both Herwig shower handlers and in Sherpa.

For quark-initiated profiles, Herwig's incoming collinear PDF legs remain
massless while MAMBO assigns the requested masses to outgoing legs. Sherpa has
one particle-mass setting and also passes those masses to incoming RAMBO
kinematics. Stock Sherpa has no separate incoming/outgoing mass switch, so this
`All`-profile convention difference remains documented.

## Flavour and Process Prescriptions

Herwig partitions the inclusive KKS cross section between four- and
five-flavour channels using the scale-dependent `VariableKKS` fermion factors
and `KKSBottomMass = 4.18 GeV`.

Sherpa uses:

```yaml
INSTANTON_INCLUDE_QUARKS: 5
INSTANTON_C_PRODUCTION_THRESHOLD: 20.0
INSTANTON_B_PRODUCTION_THRESHOLD: 100.0
```

Charm is active throughout this campaign. Sherpa switches bottom production
on sharply at 100 GeV, whereas Herwig uses the KKS mass- and scale-dependent
channel probability.

The `gg` cards contain only `g g`. Sherpa's `All` cards list 56 incoming
channels: one `gg`, ten quark/antiquark-gluon channels, twenty
distinct-flavour same-sign quark channels, and twenty-five
quark-antiquark channels. Equal-flavour same-sign states are excluded because
a one-instanton zero-mode set cannot supply both crossed legs.

Stock Sherpa applies heavy-flavour thresholds to outgoing zero modes but not
crossed incoming flavours. The tracked campaign patch applies the same
thresholds to incoming legs and rejects malformed colour-imbalanced states
before showering.

## Cross-Section Convention

Sherpa 3.0.4 multiplies the tabulated partonic cross section by an internal
`1/36`. The campaign sets:

```yaml
INSTANTON_SIGMAHAT_MODIFIER: 36.0
```

This matches the inclusive normalization used by Herwig. Shape histograms are
normalized independently by Rivet. Production summaries compare both Herwig
variations with the baseline and require agreement within three combined
integration standard deviations.

## Rivet Comparator

`QCD_INSTANTON_KKS` uses charged tracks with `pT > 0.5 GeV`,
`|eta| < 2.5`, and anti-kT `R = 0.4` particle jets with `pT > 20 GeV`.
It records two reconstructed jet-system masses:

- `jets_mreco_inclusive_eta45` uses `|eta| < 4.5` and preserves the original
  analysis definition;
- `jets_mreco_central` uses `|eta| < 2.5` to suppress forward shower and
  beam-remnant contamination.

Both are compared event by event with `instanton_mass_truth`,
`sqrt(x1*x2*s)` from the HepMC hard-process momentum fractions. This is the
direct `2 -> N` mass in Herwig and the PDG-999 mass in Sherpa. The associated
migration histograms make upward or downward shower migration explicit.

The three mass histograms cover the configured hard-mass range:

- `0..800 GeV` in `10 GeV` bins;
- `800..3000 GeV` in `50 GeV` bins.

The high-mass `320..480 GeV` selection and its jet-shape observables retain the
inclusive `|eta| < 4.5` collection for continuity. Sphericity is evaluated in
the reconstructed track- or jet-system rest frame.

Validation and summary reports include weighted and unweighted overflow
fractions for both reconstructed masses and require a valid truth mass for
every event. Existing YODA files do not contain the event records needed to
construct the new central, truth, and migration observables, so selected
samples must be regenerated once after this update.

## Setup

Activate the Herwig installation that supplies Herwig 7.3, Rivet, LHAPDF,
HepMC3, GSL, and CMake:

```sh
source /path/to/Herwig/bin/activate
```

The driver uses `SHERPA_SOURCE` when set. Otherwise it looks for Sherpa 3.0.4
at `~/Projects/Pull/summer2026_new/Sherpa/sherpa-v3.0.4`.

Check the environment and cards:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py render --check
python3 Campaigns/HerwigSherpa/run_campaign.py doctor
```

Build the Herwig matrix-element plugin, Rivet analysis, and campaign-local
Sherpa:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py build --component all
```

Build products live under `.build/` and `.local/`. Runs use the patched local
Sherpa unless `SHERPA_BIN` deliberately points to an equivalent build. The
tracked patches:

- permit the installed Rivet/HepMC3 3.2.5 combination;
- fix Sherpa 3.0.4 RAMBO's incoming-mass calculation;
- handle the final KKS table node at `2895.5 GeV`;
- apply charm and bottom thresholds to incoming instanton flavours and guard
  colour balance.

## Smoke Tests

Run the sixteen sample/profile smoke tests concurrently:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py smoke --jobs 4
python3 Campaigns/HerwigSherpa/run_campaign.py validate --smoke
python3 Campaigns/HerwigSherpa/run_campaign.py summarize --smoke
python3 Campaigns/HerwigSherpa/run_campaign.py merge --smoke
python3 Campaigns/HerwigSherpa/run_campaign.py plot --smoke
```

Smoke cards retain every process but use one 500-point Herwig integration
iteration. Their cross sections and plots are structural checks, not precision
comparisons. Merged smoke output and overlays are written below `.work/` so
they cannot be mistaken for production results.

Run the same smoke command again without `--force` to verify that every
completed shard is skipped. Use `--force` only when intentionally replacing
matching output.

## Live Tracker

Like the DISPOL campaign driver, `run` and `smoke` maintain a live campaign
tracker. In an interactive terminal the display refreshes in place and shows:

- completed, skipped, running, pending, and failed shard counts;
- completed events and events already generated by active shards;
- progress by sample/profile;
- each active shard's generator, event or integration progress, seed, and
  runtime.

The latest production snapshot is written atomically to:

```text
Campaigns/HerwigSherpa/results/monitor/status.txt
Campaigns/HerwigSherpa/results/monitor/status.json
```

Smoke snapshots use `Campaigns/HerwigSherpa/.work/monitor/`. Inspect either
snapshot from another terminal with:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py status
python3 Campaigns/HerwigSherpa/run_campaign.py status --json
python3 Campaigns/HerwigSherpa/run_campaign.py status --smoke
```

The text file is intended for people and the JSON file for scripts or batch
dashboards. Both include the campaign run ID, phase, selected samples,
profiles and shards, and their last update time. If overlapping campaign
commands are active, these paths contain the snapshot written most recently;
the run ID identifies its owner.

The default refresh interval is five seconds. It can be changed with
`--progress-interval SECONDS`; a negative value suppresses intermediate
terminal refreshes while preserving the initial and final snapshot. Use
`--max-listed N` to limit the number of active shards and incomplete
sample/profile groups shown.

## Production and Resume

The first run after this Rivet schema change must archive and replace the old
YODA products. To regenerate only the Random3 angular-shower Herwig baseline:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py run \
  --sample herwig --jobs 4 --force
```

After that migration, resume the same baseline without `--force`:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py run \
  --sample herwig --jobs 4
```

`--jobs` bounds concurrent generator subprocesses and defaults to one. Each
shard has an external file lock, so overlapping campaign commands cannot run
the same shard twice. A completed shard is skipped only when its event count,
seed, sample, profile, card, generator executable, source, plugins, and Herwig
run file match its provenance and its YODA output validates.

Matching incomplete attempts are archived under `attempts/` and retried.
Mismatched output is rejected unless `--force` is supplied; forced replacements
are archived under `superseded/`. Independent shards continue after a failure,
and the command exits nonzero with a combined failure summary.

Select samples, profiles, or shards explicitly:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py run \
  --sample herwig-qcdinsplanar,herwig-random3-dipole \
  --profile all-high --shards 0,1,2 --jobs 3
```

`--sample all` is the default. The legacy `--generator herwig` and
`--generator sherpa` spellings remain aliases for those original sample IDs.

## Merge, Validate, and Plot

Merge and inspect all results:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py merge
python3 Campaigns/HerwigSherpa/run_campaign.py validate --results
python3 Campaigns/HerwigSherpa/run_campaign.py summarize
```

Create four-way overlays and ratio panels:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py plot
```

The first selected sample is the ratio reference; the default ordering uses
Random3/angular Herwig. A focused comparison is:

```sh
python3 Campaigns/HerwigSherpa/run_campaign.py plot \
  --sample herwig,herwig-qcdinsplanar --profile all-high
```

PDF and PNG are rendered in separate passes. Generated runs, logs, YODA files,
integration databases, archived attempts, and plots are ignored. Only source,
configuration, cards, tests, patches, and documentation belong in Git.
